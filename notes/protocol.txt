MAMEUI Netplay                                              Protocol


                        THE WIRE FORMAT


Abstract

   STATUS: NOT YET DESIGNED. No packet layout, no version gate, no
   handshake exists.

   What is settled is the SHAPE of the payload and the reason for it:
   the wire format is player-relative, and it is not MAME's port
   structure. Section 1 is the constraints, all of them read out of
   code. Section 2 is the resync mechanism, settled in structure and
   sized against measurement, but not laid out. Sections 3 and 4 are the
   format itself and are empty.

   Injection into MAME happens at the port level; that is a different
   layer from this one and lives in netplay-hooks.txt 1.5. Injection is
   a plain write, not a masked one - netplay-hooks.txt 1.3.

1.  Constraints the format has to satisfy

1.1.  The payload is player-relative, not port-shaped

   THE OBVIOUS DESIGN IS WRONG. MAME's own per-frame input record is
   ioport_manager::record_port. Copying its structure onto the wire
   fails for two independent reasons, both established in
   netplay-hooks.txt.

   First, PLAYER IDENTITY IS ALREADY GONE from it - digital is one
   merged bitmask per port, with nothing in it to route. See
   netplay-hooks.txt 1.3.

   Second, every player uses the SAME keys locally, while MAME's
   default sequences are disjoint per player. See netplay-hooks.txt 1.4.
   A player must not have to learn a different keyboard because they
   joined second.

   So the payload is a compact per-player logical input word - "player
   2 pressed the button that is Button 1 for them" - and the receiving
   side maps each player's word onto that player's actual ports. The
   sender never needs to know MAME's port layout and the format never
   changes when a driver's ports change.

   This is what the 0.119 Kaillera build did, and it is the one part of
   that design worth copying wholesale. [verified:
   e:/DEV/mame32/119/src/emu/inptport.c]

   Rejecting record_port's SHAPE does not discard its value as evidence.
   Whatever record_port captures is provably sufficient to reproduce a
   session, because -record / -playback does exactly that. So its size is
   a hard UPPER BOUND on what the wire must convey, and the
   player-relative word has to be measured against it rather than
   guessed at. Per frame, record_port writes [verified ioport.cpp]:

       per port            defvalue + digital, ioport_value = u32    8
       per analog field    m_accum, m_previous, m_sensitivity s32,
                           m_reverse as u8                          13

   Measured over 18 drivers that is 32 to 158 bytes per frame, the
   maximum being offroad with 10 ports and 6 analog fields. The
   player-relative word comes to 4 to 12 bytes per player (1.6.1), so
   the chosen format is smaller than the bound as well as better routed.

   TWO FIELDS IN record_port MUST NOT TRAVEL, for opposite reasons.
   record_frame also writes a u32 speed_percent, which playback_frame
   only accumulates into m_playback_accumulated_speed for statistics -
   it never reaches machine state, and it is derived from wall clock, so
   sending it would put host entropy on the wire for no benefit.
   m_sensitivity and m_reverse are configuration, not per-frame input:
   they belong in the handshake (1.3), where a mismatch is caught once,
   rather than being retransmitted 60 times a second.

   The recorded attotime is a third case and worth keeping. playback_frame
   compares it against the live time and calls playback_end("Out of
   sync"), so MAME already carries a 12-byte-per-frame misalignment check
   of exactly the kind 1.5 argues for. [verified ioport.cpp]

1.2.  The translation table is the format

   The wire format is only meaningful alongside a table mapping

       (player, logical input id) -> (port, mask)

   built ONCE at session start by walking every port and field, because
   the metadata needed to build it is gone by injection time
   (netplay-hooks.txt 1.5).

   IT NEEDS TWO RULES, NOT ONE:

       INPUT_CLASS_CONTROLLER   the player comes from field.player()
       start and coin           the player is encoded in the TYPE -
                                IPT_START2, IPT_COIN2

   Routing start and coin by field.player() instead sends every
   player's start and coin to player 1. The reason, and the evidence,
   are netplay-hooks.txt 1.4.

   Kaillera's equivalent is kBitsPlayValues[player][bit] -> (port
   index, port mask, polarity), plus a usedkeys array recording which
   bits of the per-player word no field claims. It stole up to three of
   those spare bits to carry UI commands inside the input stream.
   [verified]

   Its Mahjong path is worth noting as precedent rather than as a
   model: 29 mutually exclusive keys compressed to a single byte index.
   The format was allowed to be game-aware where that paid. [verified]

   THE TABLE HAS TO BE TOTAL OVER DIGITAL FIELDS. PORT_CUSTOM and
   analog values are never stored in a port's digital value - they are
   recomputed on every read - so injection cannot damage them
   (netplay-hooks.txt 1.3). But every DIGITAL field is in digital, so
   any digital field the table does not cover gets zeroed by the
   injection. Service, tilt and driver-internal digital bits therefore
   need an owner in the format even though no player presses them:
   either a small shared word, or frozen at handshake. A digital field
   in neither set is a bug, not a default.

   THE SHARED SET IS NOT EMPTY AND NOT NEGLIGIBLE. Measured across 18
   drivers, every digital field resolves to either a player or the
   shared set - 0 unclassified anywhere - but the shared set runs from 1
   field (gauntlet, marble, offroad) to 17 (ffight), and is typically 6
   to 15. It is DIPSWITCH, SERVICE, SERVICE1, SERVICE2, TILT and
   per-driver oddments such as dino's Freeze. [verified,
   tools/netplay_wordsize.py]

   So the shared word is a real part of the format rather than a corner
   case, and freezing it at handshake is the cheaper of the two options:
   none of those fields is something a player presses during a match.

1.3.  The handshake has to verify, not trust

   determinism.txt 4 lists what must match between peers: the binary,
   the ROM set and -bios, the DIP and input configuration, NVRAM and
   EEPROM contents, frameskip, and -cheat off.

   Every one of those is something a peer can silently get wrong, and
   none of them announces itself from inside the emulator. The
   handshake exchanges a digest of each and refuses the session on a
   mismatch. A session that starts and desyncs three minutes later is
   far more expensive than one that refuses to start.

   NVRAM is part of this rather than a special case. A driver that
   needs a boot to initialise its NVRAM does that boot inside the
   synced session; what the handshake has to pin down is the state it
   starts from. See netplay-hooks.txt 5.2.

1.4.  Session base time travels at join

   The server chooses m_base_time for the session and broadcasts it.
   Every RTC device in MAME derives from that single value, so syncing
   it makes real-time-clock chips deterministic; not syncing it
   diverges any driver with an RTC immediately.

   determinism.txt 2.2 for the mechanism, netplay-hooks.txt 2 for the
   hook that applies it.

1.5.  Carry a frame counter in the payload

   Kaillera packed a synccount into the upper 16 bits of its 4-byte
   payload. [verified: e:/DEV/mame32/119/src/emu/inptport.c] It costs
   almost nothing and it catches the failure that is otherwise
   invisible: two peers applying input to different frames.

   USE 32 BITS, NOT 16 OR 24. At 60 Hz a 16-bit counter wraps every 18
   minutes and a 24-bit one every 77 hours; 32 bits wraps in about two
   years, which is never. The cost of the widest option is 4 bytes per
   frame, or 240 bytes per second - noise on any link built after 1998.

   The cost of the narrow option is wrap-aware comparison in every
   place a frame number is compared, tagged or reported, and wrap bugs
   surface 18 minutes into a session and never in a test. Kaillera
   packed bits because it targeted dial-up. That constraint is gone;
   the complexity it bought is not worth keeping.

   The same argument retires Kaillera's usedkeys trick (1.2). Stealing
   spare input bits for UI commands couples the UI protocol to each
   driver's port layout to save a byte. Give UI and chat their own
   message types instead.

   A frame counter is not a substitute for a state hash. A counter
   catches misalignment; only a hash of emulated state catches
   divergence while still aligned.

1.6.  Input rate tiers: batch, do not decimate

   A peer sends its input at one of six tiers. Kaillera exposed the
   same ladder as a connection setting labelled in packets per
   second, and its rungs are exactly frames-per-packet 1 through 6.

   THE TIER IS PER PEER, not per session. A receiver does not care
   how many frames arrived in one datagram; it files each frame into
   the input ring either way. What batching couples to is the
   SENDER's own delay budget (1.6.3), and that is per peer too.
   Kaillera negotiated the whole session down to the worst
   connection, which makes every player pay for one bad link.

   DEFINE THE TIER AS FRAMES PER PACKET, NOT AS A FRAME RATE. No arcade
   machine runs at exactly 60 Hz - measured from -listxml, dino is
   59.637405, mslug5 59.185606, ddpdoj 59.170000, rsgun 59.764802.
   [verified] Frames per packet is exact, integral and driver
   independent; a rate in Hz is none of those.

   +------+--------+--------------+----------------+
   | Tier | Frames | Packets/s at | Kaillera label |
   +======+========+==============+================+
   | 1    | 1      | 59.6         | LAN 60         |
   +------+--------+--------------+----------------+
   | 2    | 2      | 29.8         | excellent 30   |
   +------+--------+--------------+----------------+
   | 3    | 3      | 19.9         | good 20        |
   +------+--------+--------------+----------------+
   | 4    | 4      | 14.9         | average 15     |
   +------+--------+--------------+----------------+
   | 5    | 5      | 11.9         | low 12         |
   +------+--------+--------------+----------------+
   | 6    | 6      |  9.9         | bad 10         |
   +------+--------+--------------+----------------+

   BATCH, DO NOT DECIMATE. Sample local input EVERY frame and group
   whole frames into one packet. Do not sample at the tier rate and hold
   the value across the batch.

   The difference matters twice over. Sample-and-hold destroys
   single-frame input, which is the whole vocabulary of a fighting game,
   and it would make the tier a gameplay setting rather than a transport
   setting. Batching keeps the applied-input layer identical at every
   tier, so determinism, the translation table (1.2) and the injection
   point (netplay-hooks.txt 1.5) are all unaffected by which tier is in
   use. [inferred]

1.6.1.  The hot-path word is 8 bytes

   One fixed 8-byte word per player per frame. That is the whole hot
   path. The size is measured, not chosen for roundness: over 26
   drivers, counting each player's digital logical inputs at one bit
   plus each of that player's analog axes at its mask width
   [verified, tools/netplay_wordsize.py]:

   +----------+---------+--------+------+----------------------+
   | Driver   | Digital | Analog | Bits | What sets it         |
   +==========+=========+========+======+======================+
   | daytona  | 11      | 3      | 35   | pedal, brake, steer  |
   +----------+---------+--------+------+----------------------+
   | vr       | 8       | 3      | 32   | pedal, brake, wheel  |
   +----------+---------+--------+------+----------------------+
   | mjsister | 30      | 0      | 30   | mahjong panel        |
   +----------+---------+--------+------+----------------------+
   | royalmah | 28      | 0      | 28   | mahjong panel        |
   +----------+---------+--------+------+----------------------+
   | polepos  | 2       | 3      | 26   | pedal, brake, steer  |
   +----------+---------+--------+------+----------------------+
   | spyhunt  | 7       | 2      | 23   | pedal, paddle        |
   +----------+---------+--------+------+----------------------+
   | sf2      | 12      | 0      | 12   | joystick + 6 buttons |
   +----------+---------+--------+------+----------------------+
   | dino     | 8       | 0      | 8    | joystick + 2 buttons |
   +----------+---------+--------+------+----------------------+
   | gauntlet | 7       | 0      | 7    | joystick + 2 buttons |
   +----------+---------+--------+------+----------------------+

   MAHJONG IS NOT THE AWKWARD CASE, which is worth saying because it
   looks like it should be. Its 29-key panel plus start is 30 bits and
   fits in 32. The driver that does not fit is daytona at 35 - eleven
   digital inputs and three 8-bit analog axes. 25 of the 26 measured
   drivers fit in 32 bits; daytona is the one that does not.

   So mahjong costs nothing to support at this width. It is 30 bits of a
   word already being sent, needs no extra field and no second message
   type, and leaving it out would save zero bytes.

   EVERY ANALOG FIELD MEASURED IS 8 BITS WIDE. 33 of 35 are 0xff; the
   other two are tempest's 4-bit knobs. Nothing is wider, across
   trackballs, pedals, steering, light guns and AD sticks - marble,
   offroad, daytona, polepos, vr, starwars, sharrier, spyhunt, term2,
   lethalen, tempest. [verified]

   That is the GAME-VISIBLE width, which is the one that matters: the
   mask decides how many bits reach the driver through
   ioport_port::read(). Do not send analog as record_port's s32 m_accum.
   m_accum is an accumulator whose mapping to the port value runs through
   m_sensitivity, m_reverse, clamping and wrapping - all of it
   configuration that belongs in the handshake (1.1). Sending the
   post-mask value instead makes the payload independent of every one of
   those settings. 4 bytes per axis would be sending 24 bits of nothing.

   The layout follows directly, 32 bits of each:

       bits  0-31    digital, one bit per logical input, assigned by
                     the translation table (1.2)
       bits 32-39    analog axis 0
       bits 40-47    analog axis 1
       bits 48-55    analog axis 2
       bits 56-63    analog axis 3

   32 digital bits covers mahjong's 30. Four analog axes covers the
   measured maximum of three. A narrower axis - tempest - uses the low
   bits of its byte and the table carries the mask.

   THE MEASUREMENT IS 26 DRIVERS, AND THE STRUCTURAL BOUND IS HIGHER.
   The per-player enum blocks are DIGITAL_JOYSTICK 12, MAHJONG 29,
   HANAFUDA 10, GAMBLING 26, plus 16 action buttons. [verified
   ioport.h] Nothing says a driver may use only one of them, and one
   measured driver does not: mjsister assigns both MAHJONG and GAMBLING
   types to player 1. It still lands at 30 bits because it uses a subset
   of each, but a driver using all of both plus start and coin would be
   57 digital bits, and with three analog axes 81 - eleven bytes, not
   eight.

   So the width is justified by measurement, not by construction. The
   format does not widen speculatively to cover a driver no one has
   found; it makes the case checkable instead. The translation table is
   built at handshake, before any frame runs, so whether this driver's
   fields fit in 64 bits is known then, and a driver that does not fit
   is refused with a specific reason (4.4) rather than silently losing
   its high bits.

   FIXED, NOT PACKED PER DRIVER. The same table would equally support a
   per-driver width of ceil(bits/8) - 1 byte for dino, 5 for daytona -
   and that is still the wrong trade. A fixed slot puts frame N player P
   at a constant offset, which keeps the hot path branch-free, makes
   packet length a function of the tier alone, and makes the batching
   and redundancy arithmetic of 1.6.2 trivial. The bandwidth it costs is
   0.7 KB/s at tier 1 (below), on a link with hundreds available.
1.6.2.  What tiers actually buy, and what they do not

   NOT BANDWIDTH. Four players at 8 bytes is 32 bytes of payload per
   frame, plus the 12-byte header of section 3 and 28 bytes of UDP/IPv4:

   +------+--------------------+-----------+---------------+
   | Tier | Bytes/packet       | Packets/s | KB/s per peer |
   +======+====================+===========+===============+
   | 1    | 40 +  1 x 32 =  72 | 59.6      | 4.2           |
   +------+--------------------+-----------+---------------+
   | 2    | 40 +  2 x 32 = 104 | 29.8      | 3.0           |
   +------+--------------------+-----------+---------------+
   | 3    | 40 +  3 x 32 = 136 | 19.9      | 2.6           |
   +------+--------------------+-----------+---------------+
   | 4    | 40 +  4 x 32 = 168 | 14.9      | 2.4           |
   +------+--------------------+-----------+---------------+
   | 5    | 40 +  5 x 32 = 200 | 11.9      | 2.3           |
   +------+--------------------+-----------+---------------+
   | 6    | 40 +  6 x 32 = 232 |  9.9      | 2.2           |
   +------+--------------------+-----------+---------------+

   All figures KB/s per peer.

   2.2 to 4.2 KB/s. Carrying the previous batch again for redundancy
   doubles the payload, not the total: tier 1 becomes (40 + 64) x 59.6 =
   6.1 KB/s. Even sending record_port's structure unchanged - the upper
   bound of 1.1, 158 B/frame on offroad - would be 11.5 KB/s.

   On a DSL line moving hundreds of KB/s all of that is a rounding
   error, and the spread between the best and worst tier is 2 KB/s. ANY
   ARGUMENT FOR LOW TIERS THAT RESTS ON INPUT BANDWIDTH IS WRONG. The
   bandwidth problem in this protocol is the resync payload (2.4), which
   is three orders of magnitude larger.

   What they do buy:

   o PACKET RATE. 59.6 packets/s per peer down to 9.9. Cheap NAT
     hardware tracks state per flow and dislikes high rates, and
     there is per-packet cost at every layer regardless of size.
   o REDUNDANCY EFFICIENCY. Carrying the previous batch again in
     every packet makes loss self-repairing without
     retransmission, and the overhead of doing so shrinks as
     packets carry more frames.

   WHAT THEY DO NOT BUY IS JITTER TOLERANCE, and that is the
   opposite of how the setting looks. A high tier does not create
   slack between packets for the network to be late in - it SPENDS
   the budget the input delay provides. See 1.6.3, which is the
   one piece of arithmetic in this document worth memorising.


1.6.3.  Input delay is the jitter budget, and batching spends it

   TWO KNOBS, BOTH USER-VISIBLE: the tier K (frames per packet) and the
   input delay D (frames). Kaillera exposed only K and set D behind it.
   D is the one that decides whether a session stutters, so it does not
   get hidden here - see 1.6.4 for what happens when it is.

   D is not a buffer sitting beside the delay. It IS the buffer. With
   delay D a peer's input for frame N was captured D frames earlier, so
   the network has that long to deliver it, and that delivery window is
   the jitter tolerance. netplay_manager already holds it as m_delay and
   the input ring; there is no second mechanism to build.

   LANDMINE: BATCHING COSTS BUDGET, IT DOES NOT PROVIDE IT. A sender
   cannot transmit a batch until it has captured every frame in it, so
   the FIRST frame of each batch waits for the other K-1:

       batch covering frames [30,31,32], K=3, D=10
         frame 32 captured at sender frame 22 -> batch sent at 22
         frame 30 needed at receiver frame 30 -> budget 8 frames

       effective jitter budget = (D - K + 1) frames

   The budget varies across a batch, from D for its last frame down to
   D - K + 1 for its first, and the first is what binds. So D = K is a
   one-frame budget whatever K is: at tier 6 that is 17 ms, which
   stutters on any link worth tuning for.

   Sizing follows. At dino's measured 59.637405 Hz a frame is 16.77 ms
   (1.6), so

       D >= ceil( (one_way_delay + jitter_margin) / 16.77ms ) + K - 1

   which gives the Kaillera ladder back with the delay derived rather
   than bundled:

   +-----------+---+-------------------+----+----------+------+
   | Preset    | K | Covers OWD+jitter | D  | Felt lag | KB/s |
   +===========+===+===================+====+==========+======+
   | LAN       | 1 |  10 ms            |  1 |  17 ms   | 4.2  |
   +-----------+---+-------------------+----+----------+------+
   | excellent | 2 |  25 ms            |  3 |  50 ms   | 3.0  |
   +-----------+---+-------------------+----+----------+------+
   | good      | 3 |  45 ms            |  5 |  84 ms   | 2.6  |
   +-----------+---+-------------------+----+----------+------+
   | average   | 4 |  70 ms            |  8 | 134 ms   | 2.4  |
   +-----------+---+-------------------+----+----------+------+
   | low       | 5 | 100 ms            | 10 | 168 ms   | 2.3  |
   +-----------+---+-------------------+----+----------+------+
   | bad       | 6 | 140 ms            | 14 | 235 ms   | 2.2  |
   +-----------+---+-------------------+----+----------+------+

   [inferred] The D column is arithmetic on the formula, not measured.
   The OWD figures are what each rung is intended to cover.

   D NEED NOT MATCH BETWEEN PEERS. In netplay_manager, m_delay decides
   only which future frame a peer's own capture lands on; emulated state
   depends solely on the CONTENTS of a ring slot, which is the same set
   of words everywhere. So A can run D=3 while B runs D=12 and the
   session stays bit-identical. [verified by construction,
   netplay_manager.cpp frame_end]

   The constraint is per direction:

       for every sender Y and receiver X:
           (D_Y - K_Y + 1) * frame_time > owd(Y->X) + jitter(Y->X)

   So each peer's delay covers that peer's own outbound path, and a
   player on a bad link raises their OWN D. Only they pay the lag.
   Everyone else keeps a small D and still receives their input in time.

   The cost of asymmetry is competitive fairness: a D=3 player reacts
   faster than a D=12 player. That is a preference, not a correctness
   question, so it is a mode rather than a rule - equalising D across
   peers trades that advantage away and keeps the smoothness.

   CHANGING D MID-SESSION IS FREE, for the same reason it need not
   match: no peer but the owner ever writes those slots, so there is no
   resync and no protocol event. One rule covers both directions. Keep a
   high-water mark of the last frame published and publish to

       target = max(high_water + 1, current_frame + D)

   filling any gap by repeating the current word. Raising D by n leaves an
   n-frame gap, which the rule fills by holding the current input across
   it. Lowering D by n would re-target n frames already published, which
   the rule skips, so the input is frozen at values already committed
   rather than rewritten. A rewrite is the thing to avoid: two values for
   one frame is a desync if peers received different ones. Either way the
   artifact is n frames of held input, which is why the control law should
   move D one step at a time rather than jumping.

   That also retires fast-forward as a catch-up tool. LOCKSTEP CANNOT
   DRIFT - a peer cannot run frame N without frame N's input and cannot
   outrun the stream - so there is no backlog to burn off. The real case
   is a delay that grew and should shrink, and the cure is to lower D by
   one and wait, costing one frozen input frame per step. Emulation speed
   never changes at all. [open] The control law - when to raise, when to
   lower - is not written yet; an adaptive jitter buffer is a solved
   problem in VoIP and the same arithmetic applies.

1.6.4.  Why this targets smoothness, not latency

   SMOOTH PLAYBACK BEATS LOW INPUT LATENCY. A stutter is worse than
   200 ms of lag. Where the two conflict, this design spends latency.

   That is a choice, and the games decide it. Modern emulator netplay is
   tuned for fighting games, where the shared state is two human
   opponents: a late or missing input costs one move, against a player
   who also missed it, and minimising latency is worth the occasional
   hitch. In a co-op game the shared state is a world full of AI that
   reacts to player input, so a lost input means a character doing the
   wrong thing in a world that responds to it, and the consequences
   compound rather than cancel.

   The evidence that the trade works is Kaillera at its lowest rung:
   two peers on separate continents, ~90 and ~110 ms ping, an hour of
   bubble bobble with no stall and no desync. Reconstructing it against
   the formula above - K=6 against roughly 90 ms of OWD plus jitter -
   puts that session at D of 11 to 14, so 185 to 235 ms of input lag.
   Players described it as laggy and entirely playable. [inferred from a
   reported session, not measured here]

   The counter-evidence is later Kaillera versions, which stuttered
   badly at the SAME lowest rung. Reducing D while leaving K at 6
   collapses the budget to D - 5 frames, and at D = 6 that is one frame,
   17 ms. That is what hiding D behind a connection label permits: the
   setting a user picks for smoothness stops delivering it and the user
   has no knob to reach for. Hence 1.6.3's two knobs. [inferred - the
   mechanism matches the reported symptom; their source was not read]

2.  Resync from a savestate

   How a peer that has diverged is brought back onto the host's
   timeline. The host is authoritative by definition: it is the peer
   everyone else has agreed to match.

   The structure below is settled. The layout is section 3 and is not.

2.1.  Two options, and only two

   The host snapshots at frame S. Transit costs M frames of wall clock,
   so the state arrives when the peers are at frame S+M. That gap is
   unavoidable, and it forces a choice.

   +---+-------------------------------+----------------------------+
   | # | Apply it as                   | Consequence                |
   +===+===============================+============================+
   | A | state(S) at frame S+M, for    | every peer INCLUDING the   |
   |   | everyone                      | host jumps back M frames.  |
   |   |                               | Consistent, but it makes   |
   |   |                               | the correct peers hiccup   |
   |   |                               | to fix the broken one.     |
   +---+-------------------------------+----------------------------+
   | B | state(S) on the diverged peer | nobody else observes       |
   |   | only, which then replays      | anything at all. The host  |
   |   | inputs S..S+M to catch up     | never hiccups.             |
   +---+-------------------------------+----------------------------+

   THERE IS NO THIRD OPTION. A state from the past applied in the
   present is either stale for everybody or needs catching up by
   somebody. A design that claims to avoid both is hiding one of them.
   [inferred]

   Take B. The asymmetry is the point: the peer that broke pays, and
   the peers that did not break are untouched.

   MEASURED: dino emulates at 17.9x real time on this host, unthrottled
   with no video or sound - "Average speed: 1787.02%". [verified] So
   replaying M frames costs M/59.6/17.9 seconds: 120 frames is 112 ms,
   and 10 frames is 9 ms.

   An earlier draft here claimed "tens of milliseconds" for 120 frames.
   That was wrong by 3 to 10x, and the reasoning was wrong in a way the
   number hides: replay is cheap because a SMALL PAYLOAD MAKES M SMALL,
   not because emulation outruns any M. A 10 KB state transits in about
   one RTT, so M is a handful of frames and the replay is single-digit
   milliseconds. A 5.5 MB state (2.4) transits in seconds, M becomes
   hundreds of frames, and the replay is a visible hitch.

   THE CONVERGENCE GATE. While a peer replays, the session keeps
   producing new frames, so a peer emulating at S times real time closes
   a gap of M frames in

       M / (S - 1)   frame-times

   which diverges as S approaches 1. At S = 3.3 a 190-frame gap closes
   in 83 frame-times, about 1.4 s. At S = 1.2 the same gap takes 950
   frame-times, about 16 s. At S <= 1 resync never completes.

2.1.1.  Measured speed multiples, and a corrected assumption

   Four drivers, -str 60 -nothrottle -video none -sound none, same host.
   [verified]

   +------------+--------------+--------+-------------+--------------+
   | Driver     | Source       |  Speed | state unc.  | state comp.  |
   +============+==============+========+=============+==============+
   | dino       | cps1.cpp     |  17.9x |     0.43 MB |        13 KB |
   | crysking   | crystal.cpp  |  14.2x |    24.81 MB |      5589 KB |
   | rsgun      | stv.cpp      |   3.4x |     6.50 MB |      1246 KB |
   | brvblade   | zn.cpp       |   3.3x |     7.80 MB |      1619 KB |
   +------------+--------------+--------+-------------+--------------+

   STATE SIZE AND EMULATION SPEED ARE INDEPENDENT. An earlier draft of
   this section asserted that the drivers with the largest states are
   also the slowest, "so the two problems compound". That is false and
   crysking disproves it outright: the largest state measured, 24.81 MB,
   on a driver that runs at 14.2x. Meanwhile rsgun and brvblade carry
   mid-sized states and are five times slower. The two properties have
   to be measured separately, per driver.

   The same draft called brvblade an ST-V driver. It is zn.cpp - Sony
   ZN, PlayStation-derived hardware. rsgun is the ST-V one.

   NONE OF THESE FOUR TRIPS THE GATE. Even the slowest, at 3.3x, nets
   2.3x of catch-up. Worst case among them is brvblade: 1.6 MB over a
   500 KB/s link is ~3.2 s of transit, ~190 frames, closing in ~1.4 s.
   [inferred - arithmetic on the measured figures, not timed end to end]

   So resync is viable across two orders of magnitude of state size and
   a 5x range of emulation speed. The gate is still worth stating
   because it is a real cliff, and a driver at 1.2x would sit on the
   wrong side of it - but nothing measured so far is near it.

   THE ONE RULE THAT MAKES THIS INVISIBLE: the resyncing peer MUST KEEP
   SENDING INPUT WHILE IT CATCHES UP. Input generation does not depend
   on emulation state - the keyboard says what it says regardless of
   which frame the emulator is on. A peer that stops sending while it
   replays stalls every other peer waiting on its input, converting a
   private hiccup into a public one. That is the failure that makes
   savestate resync feel terrible in practice, and it is a policy
   mistake rather than a protocol one.

2.2.  Control plane in band, bulk plane out of band

   Split the announcement from the payload.

       IN BAND, through the server, ordered with the input stream,
       tiny: "state for frame S exists, id X, size N, digest H"

       OUT OF BAND, host direct to the requesting peer where NAT
       permits and relayed through the server only as a fallback:
       the N bytes themselves

   The state is applied when BOTH the in-band tag and the bytes are
   present. The tag is what makes the apply point deterministic, and it
   is what the 0.119 design got right by putting state events in the
   same ordered stream as input.

   CHUNKING IS MANDATORY, NOT AN OPTIMISATION. Measured states reach
   5.5 MB compressed (2.4), and three independent reasons each rule out
   sending that as one message:

   o TRANSPORT. A practical UDP datagram is ~1200 bytes before
     fragmentation; even on TCP you want bounded writes. 5.5 MB is not
     a message, it is a transfer.
   o HEAD-OF-LINE BLOCKING. A multi-megabyte payload sharing the ordered
     stream stops input flowing, which stalls every peer - the same
     failure as 2.1's rule arriving by another route.
   o PROGRESS AND ABORT. Seconds-long transfers need to be observably
     advancing and cancellable.

   AND THE HOST MUST NOT BLOCK EITHER. The instinct to "just let the
   host stall" does not work in lockstep: the host is a peer whose input
   everyone waits on, so a host that blocks while serialising or sending
   5.5 MB freezes the session exactly as a quiet resyncing peer does.
   Chunk it and interleave with the input stream at both ends.

   The split also keeps the server dumb: in the common case it forwards
   a few dozen bytes of announcement and never touches the bulk.

2.3.  A resync budget, not a resync loop

   THE FAILURE MODE TO DESIGN AGAINST: a peer desyncs, requests a
   state, applies it, desyncs again, requests again - until the relay's
   bandwidth is exhausted and the peer is dropped. Reported from
   experience with another emulator's netplay, where mid-to-late-1990s
   drivers were the worst offenders. [guess - not reproduced here, but
   obvious enough to design against]

   Three defences, in increasing order of importance:

   o Rate limit requests server side, with backoff.
   o CAP THEM. After K resyncs in one session, stop resyncing and tell
     the user, in words, that this session or this driver is
     unsupported.
   o Never resync on a timer. The trigger is a state-hash mismatch
     (1.5), so a resync only happens where there is evidence of
     divergence.

   The cap matters most, and not for bandwidth. Resync that is cheap
   and automatic converts a determinism bug into "occasional hitching",
   and the root cause is then never found. A budget converts the same
   symptom into a diagnosis: this driver desyncs, here is the frame, go
   and read determinism.txt. KEEPING DESYNCS VISIBLE IS WORTH MORE THAN
   KEEPING SESSIONS ALIVE.

2.4.  Size: measured, and it spans two orders of magnitude

   Nine drivers, sampled with tools/sta_size.py. Compressed is what a
   resync puts on the wire; uncompressed is what one rollback snapshot
   costs in RAM. [verified]

   +------------+-------------+----------------+---------+
   | Driver     |  compressed |   uncompressed |   ratio |
   +============+=============+================+=========+
   | crysking   |     5589 KB |       24.81 MB |    4.5x |
   | brvblade   |     1619 KB |        7.80 MB |    4.9x |
   | rsgun      |     1246 KB |        6.50 MB |    5.3x |
   | theglad    |       48 KB |        1.04 MB |   22.1x |
   | kov2       |       42 KB |        0.66 MB |   16.0x |
   | ddpdoj     |       34 KB |        0.41 MB |   12.3x |
   | mslug5     |       26 KB |        0.41 MB |   16.1x |
   | dino       |       13 KB |        0.43 MB |   33.5x |
   | ffight     |       11 KB |        0.43 MB |   39.3x |
   +------------+-------------+----------------+---------+

   61x spread uncompressed, 494x compressed. THERE IS NO TYPICAL SIZE,
   and an earlier draft of this section that treated ~2 MB as "the
   design point" was wrong in both directions at once.

   NOTE THE INVERSION: the large states compress WORST, 4.5x against
   39x. The small ones are mostly sparse or zeroed RAM; the large ones
   are dominated by video memory holding real image data, which is high
   entropy. So the worst case is worse than "compress it and see"
   suggests, and compression cannot be relied on to bring an outlier
   into range.

   SIZE IS A PROPERTY OF DRIVER x MAME VERSION, NOT OF THE HARDWARE.
   ram_state::get_size() sums m_typesize * m_typecount over every
   registered save_item, so it tracks how thoroughly a driver has been
   annotated for saving - which changes as drivers are worked on. The
   same game legitimately has a different state size in a different MAME
   build. The format therefore cannot encode a size class or assume a
   bound; it needs a length field sized for tens of megabytes.

   o Compress. zlib and lzma are already bundled, and even the worst
     case gains 4.5x.
   o Chunk. Not conditional - see 2.2.
   o DO NOT delta against a previously known state. It requires the
     server to track emulator state, which turns a dumb relay into a
     participant in the emulation. The bytes are not worth that.

   Caveat on the method: all nine samples are attract mode or early
   boot. The uncompressed column is exact and fixed regardless, but the
   compressed column will grow with real gameplay, so treat these as a
   lower bound on wire cost.

2.5.  This is most of rollback

   In-band frame-tagged state plus "load it and replay the inputs from
   there" IS rollback, triggered rarely over a long window instead of
   constantly over a short one.

   Build resync first and rollback becomes shrinking the window and
   calling it more often, against machinery already proven by use.
   Build rollback first and the same machinery arrives untested, in the
   hardest configuration, with no way to tell a rollback bug from a
   determinism bug. [inferred]

   What differs is the window and the source of the state:

       resync     rare, hundreds of frames, state from the network
       rollback   every frame, 2-8 frames, state from a local ring

   Both need an input history ring and restore-and-resimulate. Rollback
   additionally needs a snapshot every frame, and 2.4 says what that
   costs: dino at 445 KB is ~45 us per snapshot and 3.5 MB for an
   8-frame ring - free. crysking at 24.81 MB is ~2.5 ms per snapshot
   against a 16.7 ms frame budget, 15 per cent of the frame, and 198 MB
   for the same ring. [inferred from the measured sizes]

   So rollback is free on CPS1 and Neo Geo and marginal on ST-V. Like
   the convergence gate in 2.1, this is a per-driver property and not a
   global design choice.

3.  Packet layout

   UDP. Every datagram is self-contained and independently
   interpretable, because a lockstep protocol that needs two packets to
   make sense of one frame has reinvented TCP's head-of-line blocking
   without its retransmission.

3.1.  Byte order is little-endian

   A WIRE-FORMAT INVARIANT, not a preference. Both peers are x86-64;
   determinism.txt puts ARM out of scope, and MAME's own savestate
   header stores its signature through little_endianize_int32
   [verified save.cpp], so little-endian matches the precedent in the
   tree. Network byte order would mean a byte swap on every field on
   every packet on both ends, to serve a portability case that the
   determinism requirements have already ruled out.

3.2.  Common header, 12 bytes

   +-----+------+-------------+------------------------------------+
   | Off | Size | Field       | Meaning                            |
   +=====+======+=============+====================================+
   | 0   | u8   | type        | message type, 3.3                  |
   +-----+------+-------------+------------------------------------+
   | 1   | u8   | version     | protocol version; mismatch refuses |
   +-----+------+-------------+------------------------------------+
   | 2   | u16  | session     | assigned by the server at join     |
   +-----+------+-------------+------------------------------------+
   | 4   | u32  | base_frame  | frame number of the first frame    |
   +-----+------+-------------+------------------------------------+
   | 8   | u8   | nframes     | consecutive frames in the payload  |
   +-----+------+-------------+------------------------------------+
   | 9   | u8   | player_mask | bit p set: player p word present   |
   +-----+------+-------------+------------------------------------+
   | 10  | u8   | flags       | 3.4                                |
   +-----+------+-------------+------------------------------------+
   | 11  | u8   | reserved    | zero; receivers must not check it  |
   +-----+------+-------------+------------------------------------+

   base_frame IS 32 BITS AND IS NOT PACKED. The reasoning is 1.5's: at
   60 Hz a 16-bit counter wraps every 18 minutes, which is a bug that
   surfaces in production and never in a test. One copy per PACKET, not
   per frame - with batching the frames in a packet are consecutive by
   construction, so frame i of the payload is base_frame + i. That is
   also why nframes exists rather than being derived from the datagram
   length: the length is known, but a receiver should reject a truncated
   or padded packet rather than infer a frame count from it.

   player_mask IS A MASK, NOT A COUNT, so a packet can carry a subset of
   players. The server needs this to forward what it has when a peer's
   input is late; a count could only express a prefix.

   reserved IS NOT CHECKED BY RECEIVERS. A version-gated field that
   receivers validate cannot later be used without a version bump; one
   they ignore can.

3.3.  Message types

   +------+---------+-------------+--------------------------------------+
   | Type | Name    | Direction   | Purpose                              |
   +======+=========+=============+======================================+
   | 0x01 | INPUT   | both        | the hot path, 3.5                    |
   +------+---------+-------------+--------------------------------------+
   | 0x02 | JOIN    | peer -> srv | request to join, carries 4.2         |
   +------+---------+-------------+--------------------------------------+
   | 0x03 | WELCOME | srv -> peer | session, slot, tier, base time       |
   +------+---------+-------------+--------------------------------------+
   | 0x04 | REFUSE  | srv -> peer | reason code; session not started     |
   +------+---------+-------------+--------------------------------------+
   | 0x05 | START   | srv -> all  | first frame number, go               |
   +------+---------+-------------+--------------------------------------+
   | 0x06 | HASH    | both        | state hash at a frame, 3.6           |
   +------+---------+-------------+--------------------------------------+
   | 0x07 | DESYNC  | srv -> all  | divergence found, resync coming      |
   +------+---------+-------------+--------------------------------------+
   | 0x08 | RESYNC  | srv -> all  | bulk state, out of band (2.2)        |
   +------+---------+-------------+--------------------------------------+
   | 0x09 | STALL   | both        | I am not ready for frame N           |
   +------+---------+-------------+--------------------------------------+
   | 0x0a | CHAT    | both        | its own type, never input bits (1.5) |
   +------+---------+-------------+--------------------------------------+
   | 0x0b | BYE     | both        | leaving, with a reason               |
   +------+---------+-------------+--------------------------------------+

   Numbering starts at 1 so that a zero first byte is always a malformed
   packet rather than a valid message.

3.4.  Flags

       bit 0   HASH_TRAILER   an 8-byte state hash for base_frame
                              follows the payload
       bit 1   REDUNDANT      this packet repeats frames already sent
       bit 2   FINAL          last input packet of the session
       bits 3-7  zero

   HASH_TRAILER is how desync detection rides along. The hash is 8 bytes
   and only needs to travel on the frames actually being checked, so
   attaching it to an INPUT packet rather than giving it its own
   datagram costs 8 bytes instead of 48 and cannot arrive out of step
   with the frame it describes.

3.5.  INPUT, the hot path

       header            12 bytes, 3.2
       words             nframes x popcount(player_mask) x 8 bytes
       hash trailer       8 bytes if flags & HASH_TRAILER

   Words are ordered frame-major, then by ascending player slot, so the
   word for frame base_frame + i and the n'th set bit of player_mask is
   at a fixed offset. The 8-byte word is 1.6.1.

   At tier 1 with four players that is a 44-byte datagram, 52 with a
   hash. At tier 6 carrying one redundant batch, 12 + 12 x 4 x 8 = 396.
   Every case is far inside any MTU, so the format never fragments and
   never needs to.

3.6.  HASH

       header            12 bytes, base_frame is the frame hashed
       layout_hash        8 bytes, netplay_hash.h; handshake only
       state_hash         8 bytes

   A standalone HASH message exists for the handshake, where the layout
   hash is exchanged before any frame has run. In the session the hash
   travels as an INPUT trailer (3.4) instead.

   determinism.txt 6 records why one sampled frame is not enough: input
   that diverges is not visible in the hash on the frame it is applied,
   only on the next, because it has not reached RAM yet. Check runs of
   consecutive frames, not isolated ones.

4.  Handshake

   The handshake's job is to refuse a session that would desync, since a
   session that starts and diverges three minutes later is far more
   expensive than one that never starts (1.3).

4.1.  Sequence

       peer -> server    JOIN      identity digests, 4.2
       server            compares against the session's own
       server -> peer    WELCOME   session, player slot, tier, base time
                     or  REFUSE    reason code, 4.4
       server -> all     START     first frame number

   The tier is the WORST peer's, decided by the server as peers join
   (1.6), and travels in WELCOME. A peer joining a running session is
   not a tier renegotiation; it is a resync (2).

4.2.  What JOIN carries

   determinism.txt 4 is the authority on what must match. Each entry is
   a digest rather than the thing itself, so JOIN stays one datagram:

   +----------+-----------------------------------+--------------------------------------+
   | Field    | Digest of                         | Why                                  |
   +==========+===================================+======================================+
   | build    | binary version and OPTIMIZE level | determinism.txt 4                    |
   +----------+-----------------------------------+--------------------------------------+
   | driver   | system name and ROM set           | different ROMs, different code       |
   +----------+-----------------------------------+--------------------------------------+
   | bios     | -bios selection                   | changes executed code                |
   +----------+-----------------------------------+--------------------------------------+
   | dipsw    | every IPT_DIPSWITCH value         | changes game behaviour               |
   +----------+-----------------------------------+--------------------------------------+
   | inputcfg | the translation table itself      | 1.2; a mismatch misroutes            |
   +----------+-----------------------------------+--------------------------------------+
   | nvram    | NVRAM and EEPROM contents         | netplay-hooks.txt 5.2                |
   +----------+-----------------------------------+--------------------------------------+
   | layout   | save_manager layout hash          | netplay_hash.h; not the same machine |
   +----------+-----------------------------------+--------------------------------------+
   | perf     | frameskip, -cheat, -drc           | determinism.txt 3 and 7              |
   +----------+-----------------------------------+--------------------------------------+
   | basetime | nothing - the server sets it      | 1.4; sent back, not proposed         |
   +----------+-----------------------------------+--------------------------------------+

   THE LAYOUT HASH IS THE STRONGEST OF THESE AND THE CHEAPEST. It is one
   u64 over every registered entry's name, element size and element
   count, so it catches a different binary, a different driver, a
   different device configuration and a different MAME version in a
   single comparison, without enumerating what might differ. The others
   remain because it does not catch what it cannot see: DIP settings and
   NVRAM contents live inside entries whose SHAPE is identical.

   THE TRANSLATION TABLE IS PART OF THE IDENTITY, not a local detail.
   Two peers that resolve (player, logical input) to different (port,
   mask) pairs will route each other's input to the wrong fields while
   agreeing on every other digest. 1.2 requires the table to be total
   over digital fields; the digest is what makes that checkable between
   peers rather than only locally.

4.3.  -drc belongs here, not in the safe list

   determinism.txt 7 open questions leave DRC-versus-interpreter
   bit-equivalence unverified. Until it is read, -drc is handshake
   state: peers must agree, the same way they must agree on frameskip.

   This costs nothing for CPS1 and Neo Geo, which use no DRC at all, and
   it is the difference between a desync hunt and a refused session for
   the SH, MIPS and PowerPC drivers that do.

4.4.  REFUSE carries a reason, and the reason is specific

       0x01  version      protocol version mismatch
       0x02  build        different binary
       0x03  driver       different system or ROM set
       0x04  bios         different -bios
       0x05  dipsw        DIP or config settings differ
       0x06  inputcfg     translation tables differ
       0x07  nvram        NVRAM or EEPROM differs
       0x08  layout       savestate layout differs
       0x09  perf         frameskip, cheat or drc differs
       0x0a  full         no free player slot
       0x0b  running      session started, and it does not accept joins
       0x0c  toowide      driver needs more than 64 bits per player

   NAME THE FIELD THAT MISMATCHED. A generic refusal makes the user
   compare an entire configuration by hand. Nine of these are a
   mismatch a peer can fix, and most name a single setting; the last
   three are not configuration at all - two are capacity and toowide is
   a property of the driver, which no peer can do anything about.

5.  Open questions

   o Who may change the shared non-player digital fields mid-session,
     and whether any driver needs them changed at all. 1.2 settles that
     freezing them at handshake is the cheaper option and that the set
     is 1 to 17 fields depending on driver; it does not establish that
     nothing legitimately toggles service or tilt during a match.
   o The logical input id enumeration. Deriving it from ioport_type
     normalised to player 1 is the obvious approach, but the START and
     COIN types break that normalisation (1.2), so the enumeration is
     not simply a subrange of ioport_type.
   o Whether four 8-bit analog axes per player is enough across the
     whole coinop set. Three is the measured maximum over 26 drivers
     and every axis measured is 8 bits or narrower (1.6.1), but that is
     a sample. A portdump sweep of the full set would settle it, and
     the handshake refuses what does not fit either way.
   o Whether the server relays the INPUT stream or only brokers the
     session with peers connected directly. Relaying costs roughly 1.5x
     the peer-to-peer round trip. Undecided. Separate question from
     2.2, which is about the bulk plane only.
   o Whether any driver in the coinop set actually sits near the
     convergence cliff. Four are measured in 2.1.1 and the slowest is
     3.3x, comfortably clear; the question is whether something slower
     exists, not whether these work. A sweep of the heaviest drivers
     with -str N -nothrottle would answer it.
   o A savestate taken during real gameplay rather than attract mode, to
     put an upper bound on the compressed column in 2.4.
   o Whether any driver in the coinop set exceeds 64 bits per player.
     The structural bound is 81 bits and the measured maximum is 35
     (1.6.1). Only a sweep distinguishes 'none exist' from 'none
     sampled'.
   o The adaptive control law for D: what to measure, and the
     thresholds for raising and lowering it (1.6.3). Arrival margin
     per frame is the obvious signal; reacting to a stall means the
     stutter already happened.
   o Server-side input synthesis - holding a late player's last word
     at a deadline so nobody stalls - is CONSIDERED AND DEFERRED. It
     would not desync if the substituted word were authoritative, but
     it costs the late player their input, and 1.6.4 is why that is
     the wrong currency for these games. Revisit only if stalls turn
     out to be a real problem in practice.
   o A stalled peer stalls everyone: it stops running frames, so it
     stops capturing, so it stops publishing. Lockstep has no answer
     to this short of the deferred synthesis above. Sizing D so it
     does not happen is the whole strategy.
   o How often the state hash travels. What to hash is settled - every
     registered entry, netplay_hash.h - and so is where it rides, as an
     INPUT trailer (3.4). The interval is not: every frame costs
     nothing in bandwidth but hashes the whole save set 60 times a
     second, and determinism.txt 6 shows a single sampled frame can
     miss a divergence that the next frame shows.
   o Input delay: fixed at join, negotiated, or adaptive.
   o What K should be in 2.3, and whether it scales with session
     length.
   o Late join and spectators. A late joiner is a resync with M equal
     to the whole session, so 2.1 and 2.2 cover it structurally. Out of
     scope until lockstep works.
