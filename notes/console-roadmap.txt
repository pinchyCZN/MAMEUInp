MAMEUI Netplay                                            Design Note


                 CONSOLE SYSTEMS: SNES AND GENESIS


Abstract

   A plan for netplaying cartridge consoles - Mega Drive and SNES
   first - without adding one driver entry per game. High level and
   provisional; the point of it is to pin the few places where this is
   NOT just assembly.

   Determinism for these drivers is deliberately out of scope here.
   Nothing below has been through a two-peer hash comparison.

2.  The netplay dialog

   The dense part, and the only UI that needs care. The main MAMEUI
   changes are ordinary by comparison.

   ONE DROP LIST AT THE BOTTOM, defaulting to "MAME" with one entry per
   console below it. Selecting a console switches the dialog's mode:

   o the Select Game button opens the console picker instead of the
     arcade one, listing only that console's ROM directory

   o the "System" static becomes the console name

   o the driver edit box and the full-name static are the wrong shape
     for a file name. Hide the full-name static and widen the edit box
     in its place, carrying the cart file name.

   The roster, chat, delay, batch and the rest are mode-independent and
   do not move.

3.  Identifying the cart

3.1.  The lobby carries it; UDP does not change

   THE 14-BYTE driver FIELD STAYS THE MAME SYSTEM NAME. join_payload is
   exactly 32 bytes and completely full - u64 inputmap, u64 layout, u8
   want_players, u8 slot, char driver[14] - and "megadriv" and "snes"
   both fit it. A file name does not. [verified]

   THE CART RIDES ON THE TCP LOBBY, which is text and already
   extensible: CREATE, GAME and LAUNCH are key=value lines read by kv(),
   which returns a default for any key it does not find, so adding
   cart= is backward tolerant and costs nothing.

   NO JOIN_BYTES INCREASE AND NO PROTOCOL VERSION BUMP. This is how the
   driver name already works: the lobby distributes it, and each client
   audits its own ROMs locally in rom_gate (audit_driver). The cart is
   the same pattern one level down - the lobby distributes the name, the
   joining client finds that name in its own console ROM path, hashes
   it, and compares against the hash the host advertised.

   Launching then differs from arcade by one option: -cart FILE beside
   the existing -state handling in RunMAME.

3.2.  Why a hash as well as a name

   EVERY PLAYER USING THE SAME FILE NAME IS THE DESIGN, not a fallback.
   It is what lets a joining client find the file without a picker and
   without walking a directory hashing every cart. The name is the
   lookup key.

   The hash is what decides whether the session may start, because a
   name match that passes while the bytes differ is a silent desync:
   USA against Europe against Japan, a bad dump, a trained ROM, a .bin
   against an interleaved .smd of the same game. The name finds the
   file; the hash says it is the right one.

   Three outcomes for a joining client, all local and all cheap:

       name found, hash matches      join
       name not found                "you need shinobi.bin"
       name found, hash differs      "your copy of shinobi.bin differs"

4.  Snags

   These are the parts that are not assembly.

   DIRECT CONNECT BYPASSES THE LOBBY ENTIRELY, so a cart check that
   lives only in the lobby does not cover it. Either accept that - it is
   a development path - or mix the cart hash into one of the two digests
   JOIN already carries, which costs zero bytes and makes the UDP
   handshake refuse a mismatch too. The cost of mixing is that a refusal
   can no longer say whether the cart or the build differed, which is
   why protocol.txt 4.2 wanted separate digests in the first place.

   THE LOCAL AUDIT IS NOT A CROSS-PEER CHECK. rom_gate verifies this
   machine's ROMs against MAME's own hash database; it does not compare
   anything with the other player. For arcade the cross-peer guarantee
   is the layout digest, which catches a different driver or build but
   NOT different ROM bytes of the same driver. For a console that gap
   becomes the whole problem, because every cart is the same driver.
   The host advertising a hash and the server refusing a mismatch is
   what closes it.

   THE IMAGE OPTION MAY NOT BE A PLAIN set_value. RunMAME sets options
   with emu_options::set_value at OPTION_PRIORITY_CMDLINE, but image
   device options like cart are registered when the system is known
   rather than statically. MESSUI reaches them through swconfig.cpp and
   software_config. Whether "one more set_value" is enough is NOT
   verified, and it is the join between the two halves of this work.
   Check it before scoping the UI. [open]

   CARTRIDGE SAVE RAM IS PERSISTENT PER-PEER STATE, the same class of
   problem as the NVRAM that desynced opwolf3, and far more common on
   consoles. determinism.txt 2.2 and the NVRAM note apply unchanged.

5.  Open questions

   o Which consoles beyond Mega Drive and SNES, and does the drop list
     grow per console or per driver.

   o Whether the console picker reuses netplaypick.cpp with a different
     source, or wraps the existing SoftwarePicker.

   o Whether the software list (hash/megadriv.xml) is used at all, or
     only loose files. Loose files alone is simpler and matches the
     "same file name" design.

   o Nothing here has been measured. The first real test is a two-peer
     hash comparison on megadriv with a fixed cart; it decides whether
     any of the rest is worth building.
