1.1.  Why each one

   1. Entry point. genie resolves the executable to mainCRTStartup,
      which finds stock MAME's main() rather than MAMEUI's wWinMain.
      Setting flags { "WinMain" } suppresses genie's EntryPointSymbol and
      the /ENTRY selects the wide entry; both are needed, because the
      flag alone leaves MSVC's WinMainCRTStartup default.

      IT LINKS CLEAN EITHER WAY. The symptom of getting this wrong is a
      build that runs as plain MAME with no frontend, not an error.
      That is why it is first on the list.

      Full mechanism and evidence: build-config.txt 3.3.

   2. Duplicate source. src/osd/windows/winmain.cpp appeared twice in
      the osd_winui files list. Under GNU make both entries name the
      same object path so it builds once, and the mingw block's
      -Wl,--allow-multiple-definition absorbs the duplicate link entry.
      A .vcxproj containing one source twice gives MSB8027 and two
      compilations racing for one object path. [verified]

   3. Warnings as errors. NOWERROR=1 does not disable /WX under MSVC
      in this vintage, so warnings-as-errors survives the option that
      is supposed to turn it off. The /WX- is project-scoped to
      winui_cfg.lua, relaxing only osd_winui and qtdbg_winui; core MAME
      and the executable keep /WX, which is right because upstream
      0.210 compiled clean under vs2017.

      Full mechanism, evidence, and the ordering caveat:
      build-config.txt 3.2.

   4. alloca. MSVC declares alloca in <malloc.h>, and <windows.h> does
      not pull it in. dirwatch.cpp includes only <windows.h> and local
      headers while calling alloca three times. MinGW gets the
      declaration transitively. Certain C3861 otherwise. [verified]

1.3.  .gitignore is deny-all, so new directories need whitelisting

   Upstream's .gitignore opens with

       /*
       /*/

   which hides every top-level entry, and then re-admits the ones MAME
   wants with ! lines. [verified] The consequence is that a new
   top-level directory of ours is invisible to git until it is named:
   notes/, tools/, .claude/ and server/ were all silently untracked
   until whitelisted. CLAUDE.md survived only because line 39 is
   !/*.md.

   src/emu/netplay/ needs nothing, because !/src/ already admits it.
   [verified]

   THIS IS THE TRAP WORTH KNOWING. git status showed nothing missing -
   an ignored directory is simply absent from the output, not flagged.
   Adding a top-level directory here without a matching ! line loses
   the work at the next clone.

1.4.  NOWERROR did not work, so we made it work

   scripts/genie.lua carried an unconditional "/WX" in buildoptions for
   vs20*, which is why NOWERROR=1 left warnings-as-errors switched on
   (1.1 item 3 and build-config.txt 3.2). With a real build attempted it
   stopped being a curiosity: upstream code failed on warnings that the
   option was supposed to demote.

       src/devices/cpu/i386/i386.cpp    C4701 potentially uninitialised
       src/devices/cpu/i386/athlon.cpp  C4701
       src/mame/drivers/starrider.cpp   C4390 empty controlled statement

   [verified: Debug Win32 build output] All three are pre-existing
   upstream code, and C4701 is a Debug-only diagnosis - the optimiser
   proves initialisation in Release, so a Release build would not have
   shown it.

   The "/WX" is now
       _OPTIONS["NOWERROR"] and "/WX-" or "/WX"
   which is what the documented option always claimed to do. The
   project-scoped /WX- in winui_cfg.lua stays: it is what protects the
   winui sources when somebody builds WITHOUT NOWERROR=1.

   A cosmetic consequence worth not chasing: MSBuild emits its own
   /WX- from the default TreatWarningAsError=false, so the compiler
   reports "D9025: overriding '/WX-' with '/WX'" whenever both are
   present. That warning is noise, not a symptom. [verified]

1.5.  Variable-length arrays - 18 of them

   THE LARGEST SINGLE CLASS OF MSVC BREAKAGE IN winui, and the one a
   static read missed. VLAs are a GCC extension and not C++:

       char s[file_line.length()+1];
       char t1[strlen(path)+1];
       char source_file[temp.size()+1], tmp[2048];

   Each becomes MSVC C2131, "expression did not evaluate to a
   constant", and each takes dependent statements down with it - a
   later s[4] = 0 becomes C3863 "array type is not assignable", and a
   call passing the array becomes an ambiguous-overload error. So the
   18 declarations accounted for roughly 25 reported errors. [verified]

   The transform keeps the variable usable as char* so no dependent
   line changes:

       std::vector<char> s_buf(EXPR);
       char *s = s_buf.data();

   One site, history.cpp, declared a VLA and a fixed array in one
   comma-separated statement and had to be split by hand.

   Sizing semantics are preserved exactly, including where they were
   already questionable: treeview.cpp indexes s[4] on a buffer sized
   strlen(year)+1. That was true of the VLA too. Not ours to change.

1.6.  A const that was always wrong

   properties.cpp declared

       const char *root = win_utf8_from_wstring(FindFileData.cFileName);

   then took strrchr(root, '.') into a char* and wrote through it with
   *ext = 0. win_utf8_from_wstring is defined in that same file and
   returns char*, so the const was never right; MinGW tolerated it
   because its <string.h> declares only the C strrchr returning char*,
   while C++ <cstring> provides the const overload that MSVC correctly
   selected. [verified]

1.2.  Two things deliberately NOT changed

   src/lib/winpcap as an include directory in the ocore_winui project
   does not exist in 0.210 - src/lib holds only formats, netlist and
   util. It is a dead path from an older tree. MSVC silently ignores a
   missing /I, and the real pcap headers come from
   3rdparty/winpcap/Include via scripts/src/osd/modules.lua. Harmless;
   left alone to keep the rebase surface small. [verified]

   _WIN32_WINNT=0x0501 in winui_cfg.lua targets Windows XP against a
   Windows 10 SDK. Not yet observed to break anything at 0.210.
   [verified that the define is there; effect unmeasured]
